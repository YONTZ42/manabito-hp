## 1. Instagram連携

### 1-1. 現状の実装

```
lib/instagram.ts          → Graph API呼出し・フォールバック処理
components/sections/instagram-news-section.tsx → 表示コンポーネント
components/cards/instagram-post-card.tsx       → 投稿カード
data/instagram-posts.ts   → ダミーデータ（フォールバック用）
```

- Facebook Graph API `v23.0` で `/media` エンドポイントを呼出し
- 投稿3件を取得、1時間キャッシュ（ISR `revalidate: 3600`）
- 環境変数が未設定 or API失敗時はダミーデータにフォールバック
- フォールバック時に「ダミー投稿を表示しています」と画面表示

### 1-2. 解決すべき問題

**問題: Instagram Graph APIのアクセストークンが正しく設定されていない**

考えられる原因:

| 原因 | 確認方法 | 対処 |
|------|----------|------|
| トークンが未設定 | Vercel等のデプロイ環境で環境変数を確認 | 設定する |
| 短期トークンを使っている | Meta Developer Consoleで確認。短期トークンは1時間で失効 | 長期トークンに交換する |
| 長期トークンが失効した | 長期トークンも60日で失効する | 再取得する |
| Instagram Businessアカウントではない | Meta Business Suiteで確認 | Businessアカウントに変換する |
| User IDが間違っている | Graph API Explorerで `me?fields=id` を叩いて確認 | 正しいIDを取得する |

### 1-3. 実装方針

#### ステップ1: トークン取得・設定の手順整備

1. Meta for Developersでアプリを作成（または既存アプリを確認）
2. Instagramアカウントを **Instagramビジネスアカウント** に変換
3. Facebook Graph API Explorerで短期トークンを取得
4. 短期トークンを長期トークン（60日）に交換:
   ```
   GET https://graph.facebook.com/v23.0/oauth/access_token
     ?grant_type=fb_exchange_token
     &client_id={app-id}
     &client_secret={app-secret}
     &fb_exchange_token={short-lived-token}
   ```
5. User IDを取得:
   ```
   GET https://graph.facebook.com/v23.0/me?access_token={token}
   ```
6. デプロイ環境に環境変数を設定:
   ```
   INSTAGRAM_ACCESS_TOKEN=取得した長期トークン
   INSTAGRAM_USER_ID=取得したUser ID
   INSTAGRAM_PROFILE_URL=https://www.instagram.com/keitasakai_/
   ```

#### ステップ2: トークン自動更新（推奨）

長期トークンは60日で失効する。手動更新を忘れるとダミー表示に戻る。

**方針A: 手動更新（最小構成）**
- 60日ごとに手動でトークンを再取得・環境変数を更新
- カレンダーにリマインダーを設定
- メリット: 実装不要
- デメリット: 忘れるとサイトがダミー表示になる

**方針B: 自動更新API（推奨）**
- APIルート `/api/instagram/refresh-token` を新設
- 外部cronサービス（Vercel Cron等）で30日ごとにトークンを自動更新
- 更新後のトークンをVercel環境変数APIで書き戻す
- メリット: 運用負荷ゼロ
- デメリット: 実装コストあり。Vercel環境変数APIの利用が必要

**当面は方針Aで運用し、安定したら方針Bに移行する。**

#### ステップ3: エラー可視化の改善

現状、API失敗時のログが `catch` で握りつぶされている。

```typescript
// lib/instagram.ts の catch ブロックにログ追加
catch (error) {
  console.error("[Instagram] API fetch failed:", error);
  return buildFallbackFeed();
}
```

## 2. GA4管理ページ

### 2-1. 現状の実装

```
app/analytics/page.tsx    → ダッシュボードUI（SSR, force-dynamic）
lib/ga4.ts                → JWT認証・GA4 Data API呼出し
app/layout.tsx            → フロントエンドGA4タグ挿入（@next/third-parties）
```

- Google Service AccountでJWT Bearer認証
- GA4 Data API（v1beta）で4種類のレポートを並列取得:
  - サマリー（アクティブユーザー、PV、セッション、エンゲージメント率）
  - 7日間トレンド（日別アクティブユーザー）
  - 人気ページ（上位8件）
  - トラフィックソース（上位8件）
- 環境変数未設定時は `missing-config` 状態を表示
- API失敗時は `error` 状態を表示

### 2-2. 解決すべき問題

**問題: GA4 Data APIの認証が通っていない**

考えられる原因:

| 原因 | 確認方法 | 対処 |
|------|----------|------|
| 環境変数が未設定 | デプロイ環境で確認 | 設定する |
| サービスアカウントが作成されていない | Google Cloud Consoleで確認 | 作成する |
| 秘密鍵のフォーマットが不正 | 改行コード `\n` がリテラル文字列になっていないか確認 | 正しいフォーマットで再設定 |
| GA4プロパティへのアクセス権がない | GA4管理画面でサービスアカウントのメール確認 | 閲覧者権限を付与 |
| Property IDが間違っている | GA4管理画面 → プロパティ設定で確認 | 正しいIDを設定 |

### 2-3. 実装方針

#### ステップ1: サービスアカウントのセットアップ

1. Google Cloud Console → IAMと管理 → サービスアカウント
2. 新規作成（名前例: `ga4-reader`）
3. キーを作成（JSON形式でダウンロード）
4. JSONファイルから `client_email` と `private_key` を取得

#### ステップ2: GA4プロパティへのアクセス権付与

1. GA4管理画面 → プロパティ → プロパティのアクセス管理
2. サービスアカウントのメールアドレスを追加
3. 権限: **閲覧者**（読み取り専用で十分）

#### ステップ3: 環境変数の設定

```
GA4_PROPERTY_ID=123456789
GA4_CLIENT_EMAIL=ga4-reader@your-project.iam.gserviceaccount.com
GA4_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nMIIEv...\n-----END PRIVATE KEY-----\n"
NEXT_PUBLIC_GA_MEASUREMENT_ID=G-XXXXXXXXXX
```

**秘密鍵の設定時の注意:**
- JSONファイル内の `private_key` の値をそのまま貼り付ける
- `\n` はリテラル文字列（2文字）として環境変数に入れる
- コード側で `.replace(/\\n/g, "\n")` により実際の改行に変換される（実装済）
- Vercelの場合、環境変数の値に改行を含められるため、実際の改行で入力しても動作する可能性がある。その場合は `replace` が無害に動く

#### ステップ4: 動作確認

1. ローカルで `.env.local` に環境変数を設定
2. `npm run dev` で起動
3. `http://localhost:3000/analytics` にアクセス
4. 以下を確認:
   - サマリーカードに数値が表示される
   - トレンドチャートが描画される
   - 人気ページとトラフィックソースが表示される

### 2-4. 既知の改善余地（優先度低・今回スコープ外）

| 項目 | 内容 | 優先度 |
|------|------|--------|
| アクセス制限 | `/analytics` は現在公開状態。Basic認証等の導入を検討 | 中 |
| トークンキャッシュ | 毎リクエストでOAuthトークンを取得している。キャッシュすべき | 低 |
| エラーの部分表示 | `Promise.all` のため1つ失敗で全体が落ちる | 低 |
| 日付範囲の変更 | 28日/7日が固定。UI上で変更できない | 低 |

## 3. WordPress CMS連携

### 3-1. 目的

サイト内のコンテンツ（お知らせ、ブログ記事、事例紹介等）を、非エンジニアでも更新できるようにする。現在「お知らせ」セクションが「準備中」のまま放置されており、これを解消する。

### 3-2. アーキテクチャ方針

**ヘッドレスCMS構成を採用する。**

```
WordPress（管理画面・記事執筆）
    ↓ WP REST API (wp-json/wp/v2/posts)
Next.js（フロント表示）
    ↓ ISR（増分静的再生成）
ユーザー
```

- WordPressは管理画面としてのみ使用（テーマ不要）
- Next.jsがWP REST APIから記事データを取得して表示
- ISRでキャッシュしつつ定期的に最新化

### 3-3. WordPress側の準備

#### ホスティング

| 選択肢 | 特徴 | 推奨度 |
|--------|------|--------|
| レンタルサーバー（さくら/Xserver等） | 安価、日本語サポート、SSL標準 | 推奨 |
| WordPress.com Business | マネージド。REST API利用にはBusinessプラン以上が必要 | 中 |
| 自前VPS | 柔軟だが運用コスト高 | 非推奨 |

#### 必要な設定

1. WordPressをインストール
2. REST APIが有効であることを確認（WordPress 4.7+で標準有効）
3. パーマリンク設定を「投稿名」に変更（REST APIの動作に必要）
4. 必要に応じてカスタム投稿タイプを追加:
   - `post`（お知らせ・ブログ）→ 標準で利用可能
   - `case_study`（事例紹介）→ プラグインで追加

#### セキュリティ

- フロント表示はNext.jsが担うため、WordPressの公開URLへの直接アクセスは不要
- Basic認証またはIPアクセス制限でWordPress側を保護
- REST APIは読み取りのみ使用（公開記事の取得）。認証不要

### 3-4. Next.js側の実装

#### ステップ1: API クライアント作成

```
lib/wordpress.ts（新規作成）
```

**実装内容:**
- WP REST API v2 への `fetch` ラッパー
- 投稿一覧取得: `GET /wp-json/wp/v2/posts?_embed&per_page=10`
- 個別投稿取得: `GET /wp-json/wp/v2/posts?slug={slug}&_embed`
- カテゴリ取得: `GET /wp-json/wp/v2/categories`
- ISRキャッシュ: `next: { revalidate: 600, tags: ["wordpress"] }`（10分キャッシュ）
- 型定義: `WPPost`, `WPCategory`, `WPFeaturedMedia`

**環境変数:**
```
WORDPRESS_API_URL=https://cms.manabito.info/wp-json/wp/v2
```

#### ステップ2: お知らせ表示の実装

```
app/news/page.tsx（新規作成）     → 記事一覧ページ
app/news/[slug]/page.tsx（新規作成） → 記事詳細ページ
```

**一覧ページ:**
- WordPressから最新記事を取得・表示
- ページネーション対応
- カテゴリフィルタ（お知らせ / ブログ / 事例）

**詳細ページ:**
- `generateStaticParams` で全記事のslugを取得 → 静的生成
- `revalidate` でISR対応
- OGP用メタデータをWordPressの投稿データから生成

#### ステップ3: トップページのお知らせセクション更新

```
components/sections/instagram-news-section.tsx（既存ファイルを修正）
```

**変更内容:**
- 現在の「準備中」表示を削除
- WordPressから最新3件のお知らせを取得して表示
- 「もっと見る」ボタンで `/news` に遷移

#### ステップ4: ヘッダーナビゲーション更新

- 「最新情報」のリンク先を `/news` に設定

### 3-5. 記事のカテゴリ設計

| カテゴリ | slug | 用途 |
|----------|------|------|
| お知らせ | `news` | 会社のお知らせ、リリース情報 |
| 活動報告 | `report` | 研修・視察の実施報告 |
| コラム | `column` | SEO記事、専門知識の発信 |
| 事例紹介 | `case-study` | 導入事例、お客様の声 |

### 3-6. 確認チェックリスト

- [ ] WordPressのホスティング先を決定・契約
- [ ] WordPressをインストール・初期設定
- [ ] REST APIの動作確認（`/wp-json/wp/v2/posts` にアクセスして確認）
- [ ] `lib/wordpress.ts` を実装
